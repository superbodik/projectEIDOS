## Зачем это вообще

Лаунчер — не «кнопка Play». Это единственная точка, через которую игрок
соприкасается с проектом до запуска игры: аккаунт, обновления, новости, скины,
серверы. Если он сделан лениво, каждое обновление превращается в «скачайте
архив по ссылке в дискорде», а это смерть для беты.

Три принципа:

1. **Один аккаунт на всё.** Сайт, лаунчер и игра — одна учётка. Ник из неё
   висит над персонажем. Никаких отдельных «игровых логинов».
2. **API — единственный источник правды.** Версия, changelog, скины, доступ к
   бете живут на сервере. Лаунчер ничего не хардкодит и не парсит сайт.
3. **Всё переживает откат.** Любая раздача версионируется и имеет sha256.
   Сломали билд — переключили `latest` обратно, игроки откатились сами.

## Часть II. Лента обновлений — то, чего не хватает

Сейчас `/updates` парсит `ROADMAP.md`. Это удобно (одна правка — и сайт
обновился), но у подхода потолок:

- нельзя опубликовать хотфикс, не трогая роадмап;
- нет разделения «фича / багфикс / известная проблема»;
- лаунчер не может показать «что нового именно в вашей версии»;
- нет привязки записи к версии сборки.

### Решение: таблица `updates` + эндпоинт публикации

```
POST /api/admin/updates      Authorization: Bearer <ADMIN_TOKEN>
{
  "version": "v0.7.1",
  "title": "Геология и еда",
  "channel": "beta",
  "published_at": "2026-08-03 21:45",
  "summary": "Связная модель недр, собирательство, аккаунты.",
  "added":   ["5 геологических провинций", "Ягодные кусты", "Слоты косметики"],
  "fixed":   ["time set day уводил в полночь", "Руки рисовались в полоску"],
  "changed": ["Древо квестов 18 → 23 квеста"],
  "known":   ["Тени от деревьев ещё не реализованы"]
}
```

```
GET /api/updates?limit=20&channel=beta      публично, для сайта и лаунчера
GET /api/updates/latest                      что нового в свежей версии
GET /api/updates/<version>                   changelog конкретной сборки
```

**Схема:**

```sql
CREATE TABLE updates (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    version      TEXT NOT NULL,
    title        TEXT NOT NULL,
    channel      TEXT NOT NULL DEFAULT 'beta',
    summary      TEXT,
    body_json    TEXT NOT NULL,          -- added/fixed/changed/known
    published_at TEXT NOT NULL,
    created_at   TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE UNIQUE INDEX idx_updates_version ON updates(version, channel);
```

**Как публиковать.** Руками через curl — путь в один конец. Правильно:
`tools/publish_update.py` собирает запись **из ROADMAP.md** (заголовки с датой
уже размечены) и постит в API. То есть роадмап остаётся источником, но запись
фиксируется в базе и получает версию. Одна команда после сборки:

```bash
python tools/make_release.py --version v0.7.1
python tools/publish_update.py --version v0.7.1 --since v0.7
```

### ✅ Реализовано (03.08.2026)

`public/site/updates_store.py` + эндпоинты в `app.py`:

```
GET    /api/updates?limit=20&channel=beta   публично
GET    /api/updates/latest                   публично
GET    /api/updates/<версия>                 публично
POST   /api/admin/updates                    Bearer ADMIN_TOKEN
DELETE /api/admin/updates/<версия>           Bearer ADMIN_TOKEN
```

Публикация одной командой — `tools/publish_update.py` читает ROADMAP.md,
раскладывает записи по added/fixed/changed и постит:

```bash
python tools/publish_update.py --version v0.7.1 \
    --title "Геология, еда и аккаунты" --since 02.08.2026
```

Проверено: публикация отдаёт 201, запись читается обратно, POST без токена —
401, при незаданном `ADMIN_TOKEN` эндпоинт вообще отдаёт 404.

`--dry-run` показывает, что уйдёт, ничего не отправляя. Повторная публикация
той же версии перезаписывает запись (`ON CONFLICT ... DO UPDATE`), так что
опечатку можно исправить тем же вызовом.

⚠️ Автораскладка по категориям приблизительная: она смотрит на слова
«починено / исправлено / баг» в заголовке и подпунктах. Записи роадмапа без
даты в скобках не попадают в выборку вовсе. Если нужна точность — передайте
`added/fixed/changed` явным JSON прямо в `POST /api/admin/updates`.

⚠️ Страница `/updates` пока рендерится из ROADMAP.md напрямую. Переключить её
на таблицу — отдельная задача, не блокер.

## Часть III. Скины и косметика

В игре уже есть `PlayerAppearance`: цвета кожи/одежды, 4 слота брони,
4 слота косметики (шляпа, плащ, подвеска, аура). Сейчас это живёт только в
памяти клиента. Чтобы скины стали смыслом, нужна серверная часть.

### Модель

```sql
CREATE TABLE skins (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    slot       TEXT NOT NULL,        -- 'skin' | 'cape'
    file       TEXT NOT NULL,        -- имя в static/skins/
    sha256     TEXT NOT NULL,
    active     INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE cosmetics_owned (
    user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    cosmetic   TEXT NOT NULL,        -- идентификатор из каталога
    granted_at TEXT NOT NULL DEFAULT (datetime('now')),
    PRIMARY KEY (user_id, cosmetic)
);
```

### Эндпоинты

```
POST   /api/skins            multipart, PNG 64×64 или 64×32, ≤ 64 КБ
GET    /api/skins/me         список своих скинов + какой активен
POST   /api/skins/<id>/use   сделать активным
DELETE /api/skins/<id>
GET    /skins/<username>.png публично — движок и лаунчер тянут отсюда
GET    /api/cosmetics        каталог: что существует и что открыто игроку
```

**Валидация обязательна.** Приём произвольного PNG от пользователя — классическая
дыра. Проверять: размер файла, реальные размеры изображения, что это именно PNG
(по сигнатуре, а не по расширению), перекодировать через Pillow в чистый PNG
перед сохранением. Никогда не отдавать оригинальный байт-поток.

**Косметика не продаётся.** По ПРОГРЕССИЯ.md проект без pay-to-win. Косметика
выдаётся за прогресс: «первый кремнёвый нож», «первый кимберлит», «участник
закрытой беты». Каталог — статический JSON в репозитории, выдача — по событию
из игры.

## Часть IV. Что ещё должен уметь лаунчер

### Этап 1 — уже есть
- Вход и регистрация
- Скачивание, sha256, распаковка, запуск
- Наигранное время, список миров
- Лента изменений из API

### Этап 2 — ближайшее
- **Список серверов**: `GET /api/servers` — адрес, онлайн, версия, пинг.
  Кнопка «Играть» подключается напрямую, без ввода IP
- **Выбор версии**: играть на старой сборке, если новая сломана
- **Проверка целостности**: пересчитать sha256 установленных файлов и
  докачать битые
- **Дифф-обновления**: качать не весь zip, а изменённые файлы
- **Профиль в лаунчере**: сменить скин, посмотреть достижения, наиграно часов

### Этап 3 — когда появится мультиплеер
- **Токен сессии для сервера**: игра логинится на игровом сервере тем же
  токеном, сервер проверяет его через `POST /api/auth/verify`. Без этого
  ник над головой ничего не значит — любой введёт чужой
- **Друзья и приглашения**
- **Модпаки** (Lua уже в движке — Эпоха VIII)

### Этап 4 — эксплуатация
- **Отчёты о падениях**: `CRASH_REPORT.txt` уже пишется движком.
  `POST /api/crash` с версией, ОС и стеком — и мы видим топ падений беты
- **Метрики беты**: сколько дошло до Эпохи II, где бросают. Только агрегаты,
  без слежки за конкретным человеком
- **Флаги функций**: `GET /api/flags` — включить фичу части игроков без
  пересборки

## Часть VI. Безопасность — что нельзя забыть

1. **HTTPS обязателен в проде.** Сейчас токен ходит открытым текстом. На
   локалхосте это нормально, в интернете — нет. `COOKIE_SECURE=1` за nginx.
2. **Rate limit в памяти процесса.** Работает для одного инстанса. Пойдём в
   несколько воркеров — нужен Redis, иначе у каждого воркера свой счётчик.
3. **`ADMIN_TOKEN` не задан → админские эндпоинты отдают 404.** Это специально:
   выключено лучше, чем открыто.
4. **Загрузку файлов пускать только через перекодирование.** См. раздел скинов.
5. **Токены не логировать.** Ни в консоль, ни в отчёты о падениях.
6. **Секреты только в `.env`**, файл закрыт в `.gitignore`. Ключ Resend уже
   там — в репозиторий он не попадёт.
